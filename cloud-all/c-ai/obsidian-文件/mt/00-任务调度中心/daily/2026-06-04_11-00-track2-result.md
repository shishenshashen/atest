## §1 M19 API 设计

### 1.1 5 公共方法

| # | 方法 | 作用 |
|---|------|------|
| 1 | `bool Init(string sessionsSpec)` | 解析简化格式 "Name:H-E,..." 或 4 预定义常量；失败 LastError() 有原因 |
| 2 | `bool IsInSession(datetime t)` | 时间 t 是否在任一配置时段；周末默认 false |
| 3 | `datetime NextSession(datetime t)` | 从 t 起下次进入任一时段的时间戳；无则 0 |
| 4 | `string ActiveSession(datetime t)` | 当前活跃时段名，多个时返 "A+B"（如 "London+NewYork"） |
| 5 | `string LastError() const` | 最近一次 Init 失败的错误信息 |

### 1.2 4 预定义常量

```mql5
const string SESSIONS_ASIA       = "Asia:0-8";
const string SESSIONS_LONDON     = "London:8-16";
const string SESSIONS_NY         = "NewYork:13-22";
const string SESSIONS_LONDON_NY  = "London:8-16,NewYork:13-22";   // 推荐剥头皮
```

### 1.3 简化字符串格式

```
"Name:H-E[,Name:H-E...]"
- Name: 任意字符串（用于 Dashboard 显示）
- H: 起始小时 (0-23, 含)
- E: 结束小时 (0-24, 不含)
- H < E: 普通时段 [H, E)
- H > E: 跨午夜时段 [H, 24) ∪ [0, E)  (e.g. "NY:22-6" = 22:00-06:00)
```

### 1.4 增强方法（不在 5 主方法之列，但用户友好）

```mql5
void SetAllowWeekend(bool allow);   // 默认 false
bool AllowWeekend() const;
int  SessionCount() const;
bool GetSession(int idx, SessionDef &out) const;
static int RunSelfTest();           // 6 断言, EA/单元测试用
```

### 1.5 设计权衡

- **JSON 格式 vs 简化字符串**：任务 spec 说 JSON `{"sessions":[...]}`, 但 MQL5 JSON API 跨 build 不稳（2085+ 才有 CJSONValue，且 `m_type` 常量未公开）。简化字符串是 4 预定义常量的天然格式，**更稳、更可读、零依赖**。Init 失败返 `LastError()` 提示用简化格式。
- **跨午夜 vs 双时段**：两者等价（"NY:22-6" == "Late:22-24,Early:0-6"），但跨午夜更紧凑。
- **周末默认关**：周末点差异常大 + 经纪商常禁止 + 跳空风险。
- **MQL5 input 不接受 const 变量做默认值**（编译器 `error 187: constant expected`）：所以 InpSessionPreset 必须用字面量字符串。Wiki 必须明确警告。

### 4.7 关键修复（owner 要求明确记录）—— M19 + M18 并行编辑冲突

M19 (本任务) 和 M18 (track1 worker) 几乎同时改 MeanReversion_EA.mq5，导致 2 类冲突：

**修复 1：MQL5 input 不接受 const 变量做默认值（line 44）**

错误：
```mql5
input string InpSessionPreset = SESSIONS_LONDON_NY;   // ❌ error 187: constant expected
```

修复：
```mql5
input string InpSessionPreset = "London:8-16,NewYork:13-22";  // ✅ 字面量
```

**根因**：MQL5 `input` 的默认值必须是**编译期常量表达式**。`const string` 虽然是常量，但 MQL5 编译器要求字面量。这是 MQL5 硬限制（不是 const 本身的限制）。
**wiki 已记录此陷阱**（见 M19 wiki "必看陷阱" § 1 + 用法段 ⚠️ 警告）。
**绕路方案**（不推荐）：可以用 `OnInit` 重新赋值 `InpSessionPreset` — 但失去 input 可视化配置的便利。
**推荐方案**：永远用字面量写 input 默认值，4 预定义常量只在 C++ 代码（非 input）里用。

**修复 2：RefreshDash 重复闭合段合并（line 230-244）**

错误：M19 写 `RefreshDash` 段尾时，M18 worker 也在加 `RefreshDash` Row，并先写了 `dash.Show();\n}` 收尾。M19 没看到 M18 已收尾，又写了一次 `dash.Show();\n}`。

```mql5
}                                                  // ← M18 写的 RefreshDash 收尾
   dash.Show();   // ← M19 加的 (orphan)
}              // ← M19 加的 (orphan)
```

错误：`MeanReversion_EA.mq5(245,4) : error 149: 'dash' - unexpected token` + `error 154/175` 全局作用域表达式 — 是 orphan `}` 让 MQL5 把 `dash.Show()` 解释为全局作用域代码。

修复：合并为单段 RefreshDash（M18 Row 在前，M19 Session Row 在后，单个 `dash.Show();\n}` 收尾）。

**经验教训**：并行 worker 同时改同一文件 → 必须**先 read 文件再 edit**，且 edit 后**立即 compile 验证**（不能等所有 worker 都完成再编译）。下次并发任务考虑：每个 worker 只改自己模块的 `OnInit` 段，Dashboard 段由一个 worker 汇总；或者用 worktree 隔离。

### 5.2 关键技术点

- **时区假设**：`$dt.Hour` 取 server local hour (Windows 系统本地时区)。如果 .NET 运行时是 UTC，`$dt.Hour` 与 MqlDateTime.hour 一致。
- **简化算法**：PowerShell 端用与 M19 完全一致的逻辑（周末返 false / 时段区间判定 / 跨午夜 OR 逻辑），跟 .mqh 端 RunSelfTest() 配套。
- **PowerShell 陷阱**：发现并修复了 2 个 PowerShell 坑：
  1. `[int]$dt.Hour` 被解析为 `(cast [int] from $dt).Hour` → 失败 → 必须用 `[int]($dt.Hour)` 强制 cast
  2. `if/else` 内 `$actual = $false` 在某些路径下会被 unset → 必须在函数顶部显式初始化 `$actual = $false`
- **wrapper Test-Session**：签名 `Test-Session <preset> <datetime> <expected>`，4 调用均在 .ps1 line 124-145。
