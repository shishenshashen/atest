# 05 IM 集成踩坑

> 来源：飞书 / Telegram 桥接实战。持续补充。

## P-30 飞书回调 URL 验证失败

**症状**：

```json
{"code":40001,"msg":"invalid event callback url"}
```

**根因**：

- 回调 URL 必须**公网可访问**（飞书服务器会 GET 验证）
- 验证请求需返回 challenge echo
- daemon 默认不暴露公网，需自己用 nginx / frp 转发

**修复**：

```nginx
# nginx 配置
server {
  listen 443 ssl;
  server_name mavis.example.com;

  # 飞书验证
  location /mavis/api/im/feishu/webhook {
    proxy_pass http://localhost:15321;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
  }
}
```

或在 daemon 端开启：

```bash
mavis im config feishu --public-url "https://mavis.example.com"
```

## P-31 飞书事件订阅 scope 没勾

**症状**：

用户发消息给 bot，bot 不响应。后台显示"事件订阅"是关的。

**根因**：

飞书后台"事件订阅"页面，必须勾选：

- `im.message.receive_v1`（接收消息）
- `im.message.message_read_v1`（已读，可选）

**修复**：

1. 飞书开发者后台 → 事件订阅 → 添加事件
2. 选 `im.message.receive_v1`
3. 保存 → 飞书会重新发起 URL 验证

## P-32 Telegram bot 发 "Unauthorized"

**症状**：

```
Telegram API: 401 Unauthorized
```

**根因**：

- `--bot-token` 拼错
- token 泄露被 BotFather revoke 了
- 用了旧 token（@BotFather 里 /token 重置过）

**修复**：

```bash
# 1. 验证 token
curl https://api.telegram.org/bot<TOKEN>/getMe

# 2. 重新填
mavis im config telegram --bot-token "<NEW_TOKEN>"

# 3. 重启桥接
mavis im restart telegram
```

## P-33 私聊消息没触发 agent

**症状**：

私聊发给 bot，daemon 日志显示收到消息，但 agent 没被调用。

**根因**：

`routeStrategy` 配错。`one-session` 模式下一个 chat 一次只能有**一个**活跃 session；如果上一个 session 还在 `started` 状态，新消息会被忽略。

**修复**：

```bash
# 1. 查 session 状态
mavis im session telegram --chat-id 123456789

# 2. 如果卡住 → 强制结束
mavis session close <sessionId>

# 3. 或改路由策略
mavis im config telegram --route-strategy per-user
```

## P-34 飞书群消息只接收 @bot

**症状**：

群里发消息 bot 不响应，必须 @bot 才回。

**根因**：

- 默认 `mentionBot: true` 模式
- 飞书"@bot"语法变了：旧版 `@_user_1`，新版 `<at user_id="...">bot</at>`

**修复**：

```yaml
# ~/.mavis/im/feishu.yaml
rules:
  - match:
      chatType: group
    # 三种 @ 模式都接受
    mentionBotAny: true
  # 或完全放开（所有消息都接收）
  - match:
      chatType: group
    mentionBot: false
```

## P-35 飞书富文本（post）解析失败

**症状**：

用户发富文本（带链接 / @人），daemon 收到后 agent 报 "unsupported message type"。

**根因**：

daemon 默认只解析 `text` 和 `image` 类型。`post` 类型需要额外处理。

**修复**：

```yaml
# 启用富文本解析
im:
  feishu:
    parsePost: true
    # 把 post 转成 markdown 文本喂给 agent
    postToMarkdown: true
```

或在 hook 里做转换：

```json
{
  "name": "feishu-post-to-md",
  "agentName": "general",
  "event": "before",
  "matcher": { "toolName": "im.receive", "args.messageType": "post" },
  "action": "transform",
  "transformScript": "feishu-post-to-md.js"
}
```

## P-36 Telegram 文件下载被限速

**症状**：

用户发大文件（>20MB），daemon 下载卡住。

**根因**：

- Telegram Bot API 单文件限制 20MB（下载）/ 50MB（本地 bot API）
- 跨地区下载速度被 TG 限速

**修复**：

```bash
# 方案 A：用本地 Bot API（需自己跑 tg-bot-api 服务）
mavis im config telegram --bot-api-url "http://localhost:8081"

# 方案 B：限制最大文件
mavis im config telegram --max-file-size-mb 20

# 方案 C：让用户用网盘
mavis im config telegram --reject-large-files-message "请改用网盘链接，单文件 > 20MB 不支持"
```

## P-37 IM 速率限制触发静默丢消息

**症状**：

飞书群发 100 条消息测试，bot 只回了 80 条，后 20 条没动静。

**根因**：

- 飞书：1000 次/分钟 per app（per chat 是另一档）
- daemon 默认 batch 发送，没做精细 backoff

**修复**：

```yaml
im:
  feishu:
    rateLimit:
      perMinute: 800       # 留余量
      perChatPerSecond: 5  # 单聊每秒最多 5 条
      backoffStrategy: exponential
```

## P-38 飞书卡片（card）回调 button 不触发

**症状**：

agent 发卡片消息，点了按钮没反应。

**根因**：

卡片按钮需要配 `callback_url` 或 `action` 字段，且需在飞书后台"卡片回传"事件。

**修复**：

1. 飞书后台 → 事件订阅 → 加 `card.action.trigger`
2. 卡片 JSON 里：

```json
{
  "tag": "button",
  "text": "确认",
  "type": "primary",
  "value": { "action": "confirm", "id": "x123" }
}
```

3. daemon 端路由：

```yaml
im:
  feishu:
    cardCallback:
      enabled: true
      targetAgent: general
      # 把 value 字段直接喂给 agent 当 prompt
```

## P-39 消息分片后顺序乱

**症状**：

agent 回的 3 段消息，用户收到的顺序是 3-1-2。

**根因**：

- daemon 默认多 worker 并发 send，飞书/TG 顺序不保证
- 分片之间间隔 < 100ms，服务端会 reorder

**修复**：

```yaml
im:
  feishu:
    sendOrder: strict    # 严格顺序
    fragmentGapMs: 200   # 至少间隔 200ms
```

或用一个 session 内**强制串行**：

```bash
mavis im config feishu --send-strategy sequential
```

## P-40 IM bridge 进程崩溃后无重连

**症状**：

Telegram 桥接 daemon 重启后没自动重连，长轮询没起来。

**根因**：

- TG 用的 long-poll，daemon 重启后 webhook URL 失效
- 飞书 webhook URL 是固定的，不受影响

**修复**：

```bash
# 看 IM bridge 进程
Get-Process | Where-Object { $_.ProcessName -like "*im-bridge*" }

# 手动重启
mavis im restart telegram
mavis im restart feishu

# 配 cron 守护（见 [[01-核心模块/M04 Cron 自提醒]]）
mavis cron self im-bridge-watchdog --every 5m `
  --prompt "检查 telegram/feishu bridge 状态，断了就 mavis im restart"
```
